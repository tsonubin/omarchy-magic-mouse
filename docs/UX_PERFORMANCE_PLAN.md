## 2. UX polish (`magicmouse/cli.py`, `magicmouse/service.py` helpers)

### Help and errors

- No arguments → full help (today argparse aborts with a bare error). Every
  subcommand gets an epilog with 1–2 realistic examples.
- Errors always say what is wrong **and** the exact next command: e.g. config
  errors point at `config --show` and note the file is never touched by the
  tool; missing journalctl/editor get plain messages instead of tracebacks.
- `doctor` also answers to `diagnose` (alias).

### Guided first run: `omarchy-magic-mouse setup [--dry-run]`

Decision: **non-interactive and idempotent** (scriptable, CI-safe; a guided
flow that explains each step and stops at anything needing sudo, printing the
exact command). Steps in order:

1. config: create the default if missing, never touch an existing one;
   report the path.
2. permissions: reuse the doctor checks; for each failure print the
   copy-pasteable fix (udev rule, `input` group, `uinput` module).
3. service: if the unit is installed and systemd is available, enable+start;
   otherwise print the install command.
4. summary + next steps (`doctor`, `devices`, `config`, `log`).

`--dry-run` prints every action and changes nothing (contract tested).

### `doctor` rewrite: explain, don't just detect

Checks become `(label, status, fix)` with a `→ fix: …` line on anything not
ok, covering: uinput kernel module, udev rule installed (user or packaged
path), `input` group membership, effective node access, Hyprland session,
Hyprland `input:natural_scroll` double-flip warning (queried via hyprctl,
parsed defensively), service installed/enabled/running, config validity,
Python version. Exit 0 only when everything required passes.

## 3. Performance (`test/e2e/harness/bench.py`, `docs/PERFORMANCE.md`)

Method (emulated rig, same container as the E2E suite; run via
`test/e2e/run.sh bench`):

- **Latency**: virtual source stamps each event (monotonic); recorder stamps
  arrival on the daemon's sink → end-to-end distribution (mean/p50/p95/max)
  for pointer passthrough and for touch-scroll frames.
- **CPU per event**: daemon utime+stime from `/proc/<pid>/stat` across a
  fixed burst (pointer flood and MT-frame flood) → µs CPU per event, plus
  events/s. Idle CPU over 5s of no input must stay ~0 (no busy-poll).
- **Hot-spot profile**: cProfile over a pure-pipeline synthetic stream
  (no kernel) → top functions by cumtime.

Then fix only what the numbers justify. Expected candidates (hypotheses to
confirm or drop with data):

- uinput writes are one `os.write` per event → batch into one write per
  frame/flush (the kernel accepts multi-event writes).
- `read_events` unpacks via slicing per chunk → `struct.iter_unpack`.
- `_pump` linear-scans devices per ready fd → fd-keyed dict.

Deliverable: `docs/PERFORMANCE.md` with environment, method, before/after
tables, and any accepted overhead. If a change does not move a number, it is
reverted — no speculative micro-optimisation.
